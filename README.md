# linking-funding-landscapes

Code and reference resources for linking funding-organization strings from bibliographic metadata to OpenAlex funders and institutions, together with the figure notebook used in the associated scientific publication.

## Overview

Funding acknowledgements in large bibliographic databases are highly heterogeneous. The same organization may appear under multiple spellings, abbreviations, translations, or partial names, while OpenAlex represents funders and institutions in separate source tables. This repository provides a reproducible workflow that:

1. constructs a unified reference index of candidate funding organizations from OpenAlex and ROR;
2. matches raw Web of Science funding strings to that index using staged exact, heuristic, clustering-based, and NER-assisted rules;
3. exports intermediate and final linkage tables;
4. reproduces the paper figures from precomputed plotting tables.

The main workflow is implemented as standalone scripts rather than exploratory notebooks.

## What Is Not Included

Some large or licensed files are expected by the scripts but are not part of the versioned repository. In particular:

- `data/WOS_TSV_FUNDING_2023.feather` is the default Web of Science funding input used in stage 1;
- generated outputs under `artifacts/`, `paper_figures_output/`, and local model files under `gliner_news_small/` are created during execution rather than distributed in Git.

If your local file layout differs, most scripts allow these paths to be overridden by command-line arguments.

## Preparing `WOS_TSV_FUNDING_2023.feather`

The stage-1 matching script does not build the Web of Science funding extract itself. Users are responsible for generating `data/WOS_TSV_FUNDING_2023.feather` from the raw Web of Science XML using the vendored [`WOSRaw`](preprocessing/libraries/WOSRaw) preprocessing library.

The expected minimal schema is:

- `UID`: Web of Science record identifier
- `agency_name`: string encoding the funding entries for that record

The `agency_name` field should store the funding organizations in the format expected by [`scripts/match_stage1.py`](scripts/match_stage1.py): each funding organization is separated by `;`, and each organization may optionally be followed by `:` and the associated grant identifiers. For example:

```text
funder1:;funder2:grant123;funder3:
```

This structure corresponds to the funding formatting returned by `WOSRaw.utilities.formatFundingWOS(...)`, which serializes Web of Science funding entries as `grant_agency:grant_ids`.

A minimal extraction pattern is:

```python
from pathlib import Path

import dbgz
import polars as pl
from tqdm.auto import tqdm
import WOSRaw as wos

archive_path = Path("/path/to/WoS_2023_All.dbgz")
rows = []

with dbgz.DBGZReader(archive_path) as fd:
    for entry in tqdm(fd.entries, total=fd.entriesCount):
        funding = wos.utilities.formatFundingWOS(wos.utilities.getFunding(entry))
        if funding:
            rows.append({
                "UID": entry["UID"],
                "agency_name": ";".join(funding),
            })

pl.DataFrame(rows).write_ipc("data/WOS_TSV_FUNDING_2023.feather")
```

If you prefer to work from processed WOS tables instead of iterating over the raw archive directly, the same information can also be derived from the `UT` and `FU` fields produced by the WOSRaw extraction utilities:

- `UT` maps to `UID`
- `FU` maps to `agency_name`

The stage-1 script currently uses the `agency_name` column to build the unique funding-organization list, but retaining `UID` in the input file is strongly recommended for provenance and downstream checks.

## Environment Setup

Create or update the base environment:

```bash
conda env update -f env.yml
```

Add the optional plotting dependencies if you want to run the figure notebook:

```bash
conda env update -f env-paper.yml
```

If you plan to use the vendored preprocessing libraries, initialize the submodules after cloning:

```bash
git submodule update --init --recursive preprocessing/libraries/openalex-raw preprocessing/libraries/WOSRaw
```

## OpenAlex API Authentication

Some optional steps query the OpenAlex API. The current implementation uses an API key rather than the older `mailto` parameter.

Set the key as an environment variable before running OpenAlex-assisted steps:

```bash
export OPENALEX_API_KEY=YOUR_OPENALEX_API_KEY
```

This is used by:

- [`scripts/match_stage1.py`](scripts/match_stage1.py) for optional augmentation of high-frequency unresolved strings;
- [`scripts/check_manual_annotations.py`](scripts/check_manual_annotations.py) for validation of curated mappings.

The pipeline still runs without an API key, but those optional API-assisted steps are skipped.

## Running The Matching Pipeline

The scripted workflow has five steps:

1. build the normalized OpenAlex reference index;
2. run stage 1 matching;
3. export the GLiNER ONNX model;
4. run stage 2 NER-assisted matching;
5. run stage 3 final matching and export.

### 1. Build The Normalized OpenAlex Reference Table

```bash
python3 scripts/oa_prep.py
```

Default inputs:

- `data/openalex_institutions/funders_core+basic+ids+extra+counts.tsv`
- `data/openalex_institutions/funders_core+basic+ids+extra+counts.json`
- `data/openalex_institutions/institutions_core+basic+alternate_names+ids+geo+urls+roles+metrics.tsv`
- `data/openalex_institutions/institutions_core+basic+alternate_names+ids+geo+urls+roles+metrics.json`
- `data/v1.72-2025-10-06-ror-data_schema_v2.csv`

Main generated outputs:

- `artifacts/institutions_normalized.parquet`
- `artifacts/oa_institutions.parquet`

### 2. Run Stage 1 Matching

```bash
python3 scripts/match_stage1.py --api-key "$OPENALEX_API_KEY" --verbose
```

Default inputs:

- `artifacts/institutions_normalized.parquet`
- `data/WOS_TSV_FUNDING_2023.feather`
- `data/manual_annotations.json`

Main generated outputs:

- `artifacts/u_agencies_stage1.parquet`
- `artifacts/u_agencies_high_augmented.parquet`
- `artifacts/grant_agency_edges.csv`

Optional validation of manual mappings:

```bash
python3 scripts/check_manual_annotations.py --mode id --api-key "$OPENALEX_API_KEY"
```

### 3. Export The GLiNER ONNX Model

```bash
python3 scripts/convert_gliner_news_to_onnx.py
```

Defaults:

- model ID: `EmergentMethods/gliner_small_news-v2.1`
- output directory: `gliner_news_small`
- quantized ONNX export enabled by default

Main generated output:

- `gliner_news_small/model_quantized.onnx`

### 4. Run Stage 2 Matching

```bash
python3 scripts/match_stage2.py --verbose
```

Default inputs:

- `artifacts/u_agencies_stage1.parquet`
- `artifacts/institutions_normalized.parquet`
- `gliner_news_small/model_quantized.onnx`

Main generated output:

- `artifacts/u_agencies_stage2.parquet`

### 5. Run Stage 3 Final Matching And Export

```bash
python3 scripts/match_stage3.py --verbose
```

Default inputs:

- `artifacts/u_agencies_stage2.parquet`
- `artifacts/institutions_normalized.parquet`

Main generated outputs:

- `artifacts/wos_funders.parquet`

## Figure Reproduction

The publication figures are generated from [`notebooks/paper_figures.ipynb`](notebooks/paper_figures.ipynb).

The notebook:

- reads precomputed tables from [`plotting_data/`](plotting_data);
- writes figure files to `paper_figures_output/`;
- downloads the Natural Earth country geometry file on demand if it is not already cached locally;
- includes Polars recipes at the end for reconstructing plotting tables and DOI-comparison tables from database-specific source structures.

## Reproducibility Notes

- Script defaults target `data/...` for source inputs and `artifacts/...` for generated outputs.
- Stage 1 can be run without OpenAlex API access, but OpenAlex-assisted augmentation requires a valid API key.
- Stage 2 expects a local exported GLiNER model in `gliner_news_small/` unless alternative paths are passed through the CLI.
